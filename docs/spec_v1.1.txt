SECTION 0 — EXECUTIVE SUMMARY (for partner reading)
--------------------------------------------------------------------------------

This document instructs Codex to build a working proof-of-concept of an
Arabic-first legal knowledge system for Al-Suhaiman, runnable end-to-end in
4–6 weeks. The PoC will demonstrate the following live: a lawyer drags an
Arabic PDF court ruling onto a right-to-left web page; within thirty seconds
the system has read the document with Arabic OCR, identified its practice
area, document type, jurisdiction, parties and dates, and confirmed the
metadata back to the lawyer for one-click acceptance. A second lawyer then
searches in Arabic — typing a natural-language question — and finds the
just-uploaded document among semantically-ranked precedents alongside
recently-published regulations from at least two public Saudi sources
(Bureau of Experts laws and a SAMA/CMA regulatory feed). The lawyer opens
the document and asks a follow-up question in Arabic; the system answers in
Arabic with citations pointing to specific passages in the original
document. Everything runs inside a Saudi-resident cloud environment, with
the firm's content stored as its property, encrypted and audited. The PoC
is not the production system; it is built to prove that the Arabic-first
design, the AI quality, and the end-to-end pipeline work, so that the pilot
scope (Track 2 legacy migration, ethical walls, self-learning, multi-matter
access controls) can be committed to with confidence.

The PoC's LLM is OpenAI GPT-5, used under a documented residency exception
scoped to public regulator content and synthetic firm content only. No real
client matter, real PII, or real privileged content enters the PoC. The
pilot phase swaps GPT-5 for a Saudi-Arabia-resident model and the full
production residency posture takes effect.

2.2 DATA FLOW — UPLOAD TO RETRIEVAL

1. Browser POSTs multipart upload to /api/v1/documents (FastAPI).
2. FastAPI streams file to S3-compatible object store, key
   raw/{doc_id}/{filename}. Returns 202 Accepted with doc_id and a
   status-stream URL.
3. FastAPI enqueues ingest.process job on Celery (Redis broker).
4. Ingestion worker, in order:
   a. Pull file from object store.
   b. Detect MIME / extension. If PDF: try text extraction with
      pdfplumber. If empty / image-only PDF -> OCR.
   c. OCR: PaddleOCR PP-OCRv5 with Arabic model. Output: per-page text,
      per-page bounding boxes, mean confidence. Store OCR JSON at
      processed/{doc_id}/ocr.json.
   d. Language detection: fasttext lid.176, segment-level. Tag mixed
      documents with primary + secondary language proportions.
   e. Text normalization: Arabic-specific normalizer (alef variants -> ا,
      ta marbuta handling, tatweel removal, diacritics stripped to a
      separate text_normalized field while text_raw is preserved).
   f. Chunking: paragraph-aware, see §6.1.
   g. NER + classification: parties (CAMeL-Tools NER), dates (regex +
      dateparser for Hijri/Gregorian), document type and practice area
      (zero-shot LLM prompt via LLMClient, see §7.2), jurisdiction (regex
      + LLM fallback), keywords (KeyBERT with Arabic embeddings).
   h. PII / privilege flags: regex detectors for Saudi national ID
      (10-digit starting with 1 or 2), Iqama, IBAN, phone, email, and a
      privilege-keyword Arabic list (e.g. "سري ومحمي"، "محام-موكل").
      Flags routed to review.
   i. Dedupe: SHA-256 of normalized text; if hash matches existing doc
      -> mark as duplicate, no re-index.
   j. Embeddings: BGE-M3 dense vectors per chunk, written to pgvector.
   k. Indexing: write canonical record to PostgreSQL (documents +
      document_chunks + document_metadata); write BM25-indexable fields
      to OpenSearch with Arabic analyzer; update status to
      pending_review if quality-gate triggers, else published.
   l. Emit document.ready event with doc_id; UI polls status endpoint or
      receives via SSE.
5. Retrieval (search): FastAPI /api/v1/search -> query analyzer (Arabic
   normalization + stemming) -> parallel BM25 (OpenSearch) + dense
   (pgvector cosine) -> Reciprocal Rank Fusion (RRF, k=60) -> optional
   reranker (bge-reranker-v2-m3 on top 50) -> top 10 with snippets.
6. RAG Q&A: /api/v1/documents/{doc_id}/ask -> retrieve top-k chunks from
   that document (or scoped corpus) -> pre-flight can_send_to_external_llm
   check (§10.7) -> assemble prompt -> LLMClient.complete (GPT-5) ->
   parse cited passages -> return answer + citation map.

2.4 CROSS-CUTTING PRODUCTION CONCERNS (every component)

- Observability: every HTTP and worker handler emits a structured JSON log
  with trace_id, span_id, user_id (when present), doc_id (when relevant),
  latency_ms, outcome. Every external call (LLM, OCR, OpenSearch) wrapped
  in an OTel span. Metrics: request rate, error rate, latency histogram
  per endpoint; queue depth and worker saturation; OCR confidence
  distribution; LLM token usage and cost.
- Error handling: all worker tasks idempotent (keyed by doc_id +
  pipeline_step). Retries on transient errors with exponential backoff
  (base 2s, max 5 retries, max delay 120s). Dead-letter queue for
  permanent failures, surfaced in admin UI.
- Idempotency: upload endpoint accepts Idempotency-Key header; duplicate
  upload of same content (SHA-256) returns existing doc_id with 201 and
  X-Idempotent-Replay: true.
- Security: TLS 1.3 everywhere; mTLS between FastAPI and workers in K8s;
  at-rest encryption via storage-layer (Postgres TDE or LUKS, MinIO
  SSE-S3, EBS-equivalent); secrets via Vault; JWT signing key rotated
  quarterly; per-tenant keys deferred to pilot.
- Rate limiting: per-user (100 req/min on search, 30 req/min on uploads,
  20 req/min on Q&A) via Redis token bucket.

2.5 LLM CLIENT ABSTRACTION

Codex implements one interface; PoC ships one adapter; pilot adds a second.

```python
# backend/app/llm/base.py
from abc import ABC, abstractmethod
from dataclasses import dataclass
from typing import AsyncIterator, Literal

@dataclass
class LLMMessage:
    role: Literal["system", "user", "assistant"]
    content: str

@dataclass
class LLMResponse:
    text: str
    model: str
    input_tokens: int
    output_tokens: int
    finish_reason: str
    latency_ms: int
    raw: dict  # for audit/debug

class LLMClient(ABC):
    @abstractmethod
    async def complete(
        self,
        messages: list[LLMMessage],
        *,
        max_output_tokens: int = 1500,
        temperature: float = 0.2,
        response_format: Literal["text", "json_object"] = "text",
        timeout_s: int = 30,
        request_id: str | None = None,
    ) -> LLMResponse: ...

    @abstractmethod
    async def stream(
        self,
        messages: list[LLMMessage],
        *,
        max_output_tokens: int = 1500,
        temperature: float = 0.2,
        timeout_s: int = 60,
        request_id: str | None = None,
    ) -> AsyncIterator[str]: ...
```

POC ADAPTER: OpenAIChatGPTClient wraps openai Python SDK against
api.openai.com. Reads OPENAI_API_KEY from Vault. Reads model name from
LLM_MODEL env var, default "gpt-5". Reads LLM_FALLBACK_MODEL, default
"gpt-4.1". Reads LLM_TIMEOUT_MS, default 30000.

PILOT ADAPTER (stub in repo, not active): KSAResidentLLMClient placeholder
file with NotImplementedError so the contract is visible.

SECTION 4 — TRACK 1 EXTERNAL CONTENT CONNECTORS

Codex implements three connectors for the PoC. Each is a Celery Beat
scheduled task plus a fetcher class; all three share BaseConnector.

4.1 COMMON CONNECTOR CONTRACT

```python
class BaseConnector(ABC):
    connector_id: str          # e.g. "boe_laws_v1"
    schedule_cron: str         # e.g. "0 */6 * * *"
    user_agent: str            # "ETHKA-Suhaiman-KM/1.0 (+legal@ethka.dev)"
    rate_limit_rpm: int        # requests per minute
    timeout_seconds: int       # default 30

    @abstractmethod
    def list_items(self, since: datetime) -> Iterator[ConnectorItem]: ...

    @abstractmethod
    def fetch_item(self, item: ConnectorItem) -> RawContent: ...

    @abstractmethod
    def parse(self, raw: RawContent) -> CanonicalDocumentDraft: ...

    # Common helpers (in BaseConnector):
    # - session with retry/backoff (urllib3 Retry: 5 attempts, backoff 2^n,
    #   status_forcelist=[429, 500, 502, 503, 504])
    # - robots.txt check via reppy on startup; refuses to run if disallowed
    # - rate-limit token bucket (Redis-backed)
    # - identification header always sent
    # - Arabic charset detection: assume UTF-8; if bytes invalid, try cp1256;
    #   emit metric connector.encoding_fallback
    # - schema-drift detection: hash of source field-set per item; alert if
    #   hash changes
    # - kill switch: Redis key connector:{id}:enabled checked every iteration
    # - idempotency: dedupe by source_url + content hash before persisting
    # - observability: span per item, log connector_id/item_id/outcome/duration
```

4.2 CONNECTOR C1 — BUREAU OF EXPERTS (BOE) LAWS

Source: Bureau of Experts at the Council of Ministers — official Saudi
laws and regulations database. Public laws linkable via pattern
https://laws.boe.gov.sa/BoeLaws/Laws/LawDetails/{guid} as used in
published Saudi legal references.

Access method: structured scraping of the public laws portal (no official
open API as of 2026). Server-rendered HTML, content in Arabic UTF-8.

Legal posture paragraph: BOE is a Saudi government body publishing the
law of the land. Saudi laws and regulations are not subject to copyright
in the same manner as private works; reproduction and republication for
legitimate research and professional use by licensed law firms is the
established norm in the Saudi legal market. The connector identifies
itself in the User-Agent, respects robots.txt, limits request rate (≤6
rpm), fetches only published-law pages (not transactional services), and
stores the source URL so users can return to the official source. If BOE
publishes an official API during pilot, the connector switches to that.

Endpoint pattern:
- List: https://laws.boe.gov.sa/BoeLaws/Laws/Search?lang=ar&sortby=DateOfIssue&sortdir=desc&page={n}
- Detail: https://laws.boe.gov.sa/BoeLaws/Laws/LawDetails/{guid}?lang=ar
- Translation (if available): ?lang=en

Auth: none (public).
Rate limit: 6 rpm, 1 concurrent request.

Headers:
  User-Agent: ETHKA-Suhaiman-KM/1.0 (+legal@ethka.dev)
  Accept: text/html,application/xhtml+xml
  Accept-Language: ar,en;q=0.5
  From: legal@ethka.dev

Request flow:
1. Fetch list page 1, parse, find newest item dates.
2. If newest dates >= last_seen_date, walk pages 1..N until items older
   than last_seen_date.
3. For each new GUID, fetch detail page in Arabic and English (if
   available).
4. Parse with BeautifulSoup; extract title, decree number, Hijri date,
   body text, attachments (PDFs).
5. Download attachments to object store.
6. Build CanonicalDocumentDraft, emit to ingestion queue.

Response schema (parsed):
```json
{
  "guid": "25df73d6-0f49-4dc5-b01...",
  "title_ar": "...",
  "title_en": "...",
  "decree_number": "م/191",
  "date_hijri": "1444-11-29",
  "date_gregorian_inferred": "2023-06-19",
  "volume": "Commerce, Economy, and Investment Laws",
  "body_ar": "<full text>",
  "body_en": "<full text or null>",
  "attachments": [{"url": "...", "filename": "..."}]
}
```

Schema drift: maintain field_set_hash per item; on mismatch raise alert
connector.schema_drift and quarantine the item.

Retry policy: 5 retries, exponential backoff 2^n seconds, status_forcelist
[429, 500, 502, 503, 504]. 429 waits Retry-After header.

Idempotency: key = SHA-256 of (connector_id, guid, content_hash).
Re-fetch always allowed; persist skipped if key exists.

Observability:
- Metric connector.boe_laws.items_fetched_total{outcome=success|new|duplicate|error}
- Metric connector.boe_laws.last_success_timestamp
- Log fields: connector_id, guid, outcome, duration_ms, bytes
- Alert: no successful run in 24h -> page on-call.

Kill switch: Redis key connector:boe_laws_v1:enabled = false halts next
scheduled run within ≤1 minute.

Acceptance criteria:
- AC-C1.1: connector runs every 6 hours, fetches at least 1 new item
  within first 48 hours.
- AC-C1.2: parsed item contains non-empty title_ar, body_ar, date_hijri,
  decree_number.
- AC-C1.3: Arabic encoding correct (UTF-8) — automated test asserts random
  sample contains valid Arabic characters and no mojibake.
- AC-C1.4: graceful handling of 404 on stale GUID (skip, log, continue).
- AC-C1.5: robots.txt re-check at startup; refuses to operate if
  disallowed.

5.1 UPLOAD PIPELINE (PDF / DOCX drag-and-drop)

UI: see §8 for Arabic-first upload screen.

Server pipeline (sequence in text):

User -> POST /api/v1/documents (multipart)
  - FastAPI validates: max 100MB, ext in {.pdf, .docx, .doc, .jpg, .png, .tiff}
  - Compute SHA-256 while streaming to MinIO
  - Insert documents row (status='uploaded')
  - Insert audit_log (action='upload')
  - Enqueue Celery: ingest.process(doc_id)
  - Return 202 + {doc_id, status_url}

ingest.process(doc_id):
  - Update status='processing'
  - Step 1: text extraction
      - if .docx -> python-docx
      - if .pdf with text -> pdfplumber
      - if .pdf scanned or image -> PaddleOCR
      - if .pdf mixed -> page-by-page
  - Step 2: Arabic OCR when needed
      - rasterize PDF pages at 300 DPI
      - PaddleOCR PP-OCRv5 Arabic model
      - collect per-page mean confidence
      - if mean < 0.6 -> flag low-confidence, still proceed
  - Step 3: language detection (fasttext)
  - Step 4: dedupe (sha256 vs documents.content_hash_sha256)
      - if match -> status='duplicate_of', link, return
  - Step 5: chunking (§6.1)
  - Step 6: NER + classification + keyword extraction (§7)
  - Step 7: PII detection (regex + spaCy/CAMeL)
  - Step 8: privilege detection (§10.3 keyword list)
  - Step 9: embedding generation (BGE-M3 per chunk, batch of 32)
  - Step 10: persist chunks to PostgreSQL + pgvector
  - Step 11: index BM25 fields to OpenSearch
  - Step 12: apply quality gate (§5.4)
      - if new contributor -> status='pending_review'
      - if privilege_flag=true -> status='pending_review'
      - else -> status='published'
  - Step 13: emit document.ready event (SSE channel)
  - Step 14: update metrics, emit audit_log

Total latency target: ≤30 seconds for typical 5–15 page Arabic PDF on
demo hardware (single GPU node).

Failure modes:
- OCR engine error -> retry once, fall back to Tesseract; if both fail,
  status='processing_failed', surface in admin UI.
- Embedding model timeout -> retry with smaller batch; persistent failure
  -> status='processing_failed'.
- Classification returns low confidence on all candidates -> fields left
  blank, user prompted in confirmation screen.
- Disk / storage full -> 507 to client, alert on-call.

5.2 MANUAL ENTRY FLOW (new opinion / memo)

Arabic structured form. Fields, RTL order:
- نوع المستند (drop-down: legal_opinion / memo / precedent_note / template)
- العنوان (text, Arabic, required)
- مجال الممارسة (multi-select chips, Arabic labels)
- الاختصاص القضائي (drop-down)
- التاريخ — هجري / ميلادي toggle, both editable
- ملخص تنفيذي (textarea, Arabic, optional)
- المتن (rich text area, Arabic, required)
- الكلمات المفتاحية (chip input, Arabic, auto-suggest from existing tags)
- الأطراف (party rows, name_ar + role)
- نطاق الإطلاع (radio: firm-wide / practice-area-only / restricted)
- مرفقات (optional file attach)

Auto-save: every 5 seconds, draft to documents with status='uploaded',
then on submit moves to the same pipeline as upload (skipping OCR).

5.3 CONFIRMATION SCREEN (post-upload)

After Step 13, lawyer sees auto-detected metadata. Each field has:
- Detected value in Arabic
- Confidence indicator: high (green dot, ≥0.85), medium (amber,
  0.6–0.85), low (red, <0.6)
- Inline edit on click
- "Why this value?" tooltip showing source span from OCR text

Single button "تأكيد وفهرسة" commits metadata. Secondary "حفظ كمسودة"
keeps editable. Closing page leaves doc in pending_review.

5.4 QUALITY GATE

Configurable, defaults:
- New contributor (fewer than 5 published docs with no review rejection):
  all uploads -> pending_review.
- Established contributor (5+ clean): auto-publish unless privilege_flag
  or visibility=restricted_matter.
- Override: KM Lead can promote a user to "auto-publish" in admin UI.

Quality gate is a single Python function
compute_publish_status(user, doc, flags) -> Status so it's testable.
Thresholds are config, not code.

SECTION 6 — RAG LAYER
--------------------------------------------------------------------------------

6.1 CHUNKING STRATEGY FOR LEGAL ARABIC

Legal Arabic has long, comma-rich sentences and numbered/bulleted
clauses. Fixed-window chunking destroys citation integrity. Strategy:

1. Paragraph-aware primary split: split on double-newline, then on
   Arabic-aware sentence boundaries (؟ ! . and standalone newlines).
2. Citation pattern preservation: detect Arabic legal markers (المادة /
   Article, الفقرة / Paragraph, البند / Item) — never split inside the
   span between a marker and its referenced number/letter. Regex:
   (?:المادة|الفقرة|البند)\s+(?:[\u0660-\u0669\u0030-\u0039]+|[أبجدهوزحطيكلمنسعفصقرشتثخذضظغ])
   is a non-splittable atom.
3. Target chunk size: 400–600 tokens (BGE-M3 tokenizer), max 800.
   Overlap 80 tokens.
4. Heading carry-forward: each chunk carries the most recent heading as
   a prefix [heading] ... chunk text ...
5. Page mapping: store page_no, paragraph_no, char_start, char_end so
   citations jump to source.
6. Sentence-aware chunking specifically benefits Arabic.

6.2 EMBEDDING MODEL

Chosen: BGE-M3, 1024-dim dense vectors, self-hosted on single GPU
(A100 / H100 in KSA). Tokenizer max length 8192.

Why: see §2.3. Strongest open multilingual embedding for Arabic legal
retrieval, runs in-region, supports hybrid (dense + sparse + multi-vector)
outputs from one model.

Alternatives held in reserve: multilingual-e5-large if BGE-M3 GPU
unavailable; silma-embeddings-matryoshka for Arabic fine-tuning in pilot.

Batching: 32 chunks per batch, FP16. Expected throughput ~500 chunks/sec
on H100, ~200 on A100, ~30 on CPU fallback. PoC sizing assumes single
A100.

6.3 VECTOR STORE CONFIGURATION

pgvector 0.7+ with HNSW:
- embedding VECTOR(1024)
- HNSW index: m=16, ef_construction=200
- Query-time ef_search = 100
- Distance: cosine (vectors L2-normalized at write)

6.4 HYBRID RETRIEVAL

Per query:
1. Lexical (BM25) against OpenSearch with Arabic analyzer chain:
     tokenizer: standard
     filter: lowercase, arabic_normalization, arabic_stemmer,
             decimal_digit, asciifolding
     custom synonyms (admin-editable file in PoC, no UI)
   Top 50 results, BM25 score.
2. Dense against pgvector: top 50 by cosine.
3. Fusion: Reciprocal Rank Fusion with k=60:
     score = sum(1 / (k + rank_i))
4. Optional rerank: top 30 -> bge-reranker-v2-m3 -> top 10. Enabled if
   p95 latency budget < 2s allows; toggle via env var.
5. Filter post-rank by user's visibility scope (firm_wide /
   practice_area / restricted).

6.5 CITATION TRACKING

Every chunk has stable (doc_id, chunk_index, page_no, paragraph_no).
System prompt forces citation format [¶N] where N is paragraph_no of
chunk used. API returns:
{answer, citations: [{marker, doc_id, chunk_id, page_no, paragraph_no,
char_start, char_end, quoted_text}]}

6.6 RAG PROMPTS

System prompt (final, Arabic):

أنت مساعد قانوني داخلي لمكتب السحيمان للمحاماة والاستشارات القانونية.

مهمتك: الإجابة على أسئلة المستخدم استناداً حصراً إلى المقاطع المرفقة من المستندات.

قواعد ملزمة، يجب الالتزام بها كلها دون استثناء:

١. لغة الإجابة هي اللغة العربية الفصحى، حتى إذا كان السؤال أو المقاطع تحتوي على نصوص إنجليزية. لا تجب بالإنجليزية إلا إذا طلب المستخدم صراحةً ذلك.

٢. لا تستخدم أي معلومة من خارج المقاطع المرفقة. إذا كانت المقاطع لا تكفي للإجابة بدقة، قل صراحةً وبدون اعتذار:
   "المقاطع المتاحة لا تكفي للإجابة بدقة، يُنصح بمراجعة المستند الأصلي."

٣. أدرج بعد كل ادعاء قانوني مرجعه على شكل [¶رقم] حيث الرقم هو رقم الفقرة المرجعية الوارد في المقاطع. لا تخترع أرقام فقرات.

٤. لا تخترع أحكاماً أو مواد أو أنظمة قانونية لم ترد نصاً في المقاطع. وإذا أشار المقطع إلى مرجع خارجي (نظام، لائحة، حكم) دون نص كامل، اكتفِ بذكر الإشارة دون استنباط محتوى المرجع.

٥. حافظ على المصطلحات القانونية كما وردت في المقطع. لا تُترجم المصطلحات العربية، ولا تستبدل مصطلحاً بمرادف عام.

٦. إذا تعارضت المقاطع، أوضح التعارض ولا تُرجّح أحدها إلا إذا أوضح أحد المقاطع صراحةً أنه ناسخ أو معدّل للآخر.

٧. أسلوب الإجابة: مباشر، دون مقدمات إنشائية مثل "بناءً على المقاطع" أو "يسعدني". ابدأ بالخلاصة، ثم اشرح، ثم أرفق المراجع.

User message template:

السؤال: {user_question}

المقاطع المرجعية (من مستند: {doc_title_ar}):
[¶1] {chunk_1_text}
[¶2] {chunk_2_text}
[¶3] {chunk_3_text}
...

الرجاء الإجابة وفق القواعد أعلاه.

Call parameters:
- model = "gpt-5"
- temperature = 0.1 (legal Q&A wants determinism)
- max_output_tokens = 1200
- response_format = "text"
- timeout_s = 25 (with 5s buffer under the 30s API timeout)

REFUSAL PRE-FILTER: if retrieval returns fewer than 2 chunks with
similarity >= 0.55, the system does NOT call GPT-5 — returns canned
Arabic refusal: "لا توجد مقاطع كافية ذات صلة بالسؤال داخل هذا المستند.
حاول إعادة صياغة السؤال أو توسيع نطاق البحث." This saves cost and
prevents hallucination on weak retrieval.

7.1 SEMANTIC SEARCH (Arabic + mixed)

Input: query string, optional filters (practice_area, doc_type,
jurisdiction, date range).

7.2 AUTO-TAGGING ON INGESTION

Practice area + doc type: zero-shot LLM classification via LLMClient.

Prompt:
system: أنت مصنّف قانوني آلي. مهمتك تحديد نوع المستند ومجال الممارسة بناءً على النص المقدم.
الإجابة يجب أن تكون JSON صالحاً فقط، دون أي شرح إضافي.

user: المقتطف:
{first_2_chunks_of_doc}

العنوان المقترح: {filename_or_title}

أجب بـ JSON بالشكل التالي:
{
  "doc_type": "<one of: judicial_ruling, legal_opinion, memo, pleading, contract, engagement_letter, regulation, royal_decree, council_resolution, circular, template, precedent_note, other>",
  "doc_type_confidence": <0.0-1.0>,
  "practice_area": ["<one or more of: corporate_commercial, litigation_dispute, banking_finance, real_estate, labor_employment, regulatory_compliance, ip, tax_zakat, construction, family_inheritance, criminal, administrative>"],
  "practice_area_confidence": <0.0-1.0>,
  "rationale_ar": "<short Arabic justification>"
}

Call parameters:
- model = "gpt-5" (configurable down to "gpt-4.1" via env)
- temperature = 0.0
- max_output_tokens = 400
- response_format = "json_object"
- timeout_s = 15

JSON parse failure (rare with json_object): one retry with stricter
reminder; second failure -> fields left blank, doc to review.

Parties (Arabic NER): CAMeL-Tools MSA NER on full doc text, post-filtered
to PERSON and ORG, deduplicated, top-5 by frequency, role assigned via
heuristic (first ORG mentioned as claimant if doc_type=judicial_ruling,
else party_a).

Jurisdiction: keyword lookup table first ("المملكة العربية السعودية" ->
KSA, "محكمة التجارية بالرياض" -> KSA, "DIFC" -> DIFC, etc.); LLM
fallback if no match.

Dates: Hijri-Arabic regex
\b(1[3-5][0-9]{2})[\/\-\\](0?[1-9]|1[0-2])[\/\-\\](0?[1-9]|[12][0-9]|3[01])\b
and Gregorian variant; conversion via hijri-converter Python package.

Latency target: all auto-tagging in parallel, total ≤ 10s.

Accuracy target: measured on 20-doc fixture set; ≥80% practice_area
correct, ≥85% doc_type correct.

Human override: every detected field editable in confirmation screen
(§5.3). Override events write to audit_log with action="tag_correction"
and original + corrected values, ready to feed pilot's classifier
retraining loop.

8.1 GLOBAL UI RULES

- <html dir="rtl" lang="ar"> by default; toggle to dir="ltr" lang="en"
  only when user sets English preference.
- Primary UI font: IBM Plex Sans Arabic, weights 400/500/600/700;
  fallback Tajawal, system-ui.
- Body/document reading: Noto Naskh Arabic, weights 400/700; fallback
  Amiri, serif.
- Line height: 1.7 for Arabic body text (accommodates diacritics
  without crowding); 1.5 for UI labels.
- Text justification: text-justify: inter-word (browsers' default
  kashida-based justification unreliable; inter-word avoids ragged
  right edges on Arabic).
- Numerals default: Western (0123) since most Saudi legal practitioners
  read both fluently and Western numerals copy/paste cleanly. User
  toggle in Settings for Hindi-Arabic (٠–٩).
- Dates: Gregorian primary, Hijri secondary in parentheses, e.g.
  "2024-03-12 (1445-09-02 هـ)". User toggle reverses primary/secondary.
- Logical CSS: margin-inline-start, padding-inline-end,
  border-inline-start. No left/right.
- Tailwind RTL classes (rtl:ml-4 ltr:mr-4) for exceptions.
- Icons: directional icons (arrows, chevrons) mirror via CSS
  transform: scaleX(-1) in RTL.
- Keyboard: support Arabic keyboard layout (browser handles input). All
  keyboard shortcuts work the same; document in both languages.
- Screen reader: lang="ar" on Arabic regions, lang="en" on English
  islands within mixed pages, ARIA labels in Arabic.
- WCAG 2.1 AA contrast minimum 4.5:1.
- Color palette: neutral grayscale base, single accent (deep teal
  #0F766E — works for both directions, accessible). Avoid culturally-
  loaded colors.

10.7 PDPL HANDLING AND THE POC RESIDENCY EXCEPTION

The PoC operates OUTSIDE the production residency posture stated in the
ETHKA brief, under a written exception scoped as follows. ETHKA produces
this as a one-page addendum signed by the Managing Partner of
Al-Suhaiman BEFORE any document is uploaded to the demo environment.

SCOPE OF EXCEPTION:
- The PoC environment is a demo environment, not production.
- The only content processed by GPT-5 is: (a) public regulator content
  acquired via Track 1 connectors (BOE, SAMA, National Platform), and
  (b) synthetic firm-resembling content authored by ETHKA and
  pre-approved by Al-Suhaiman.
- No real client matter, no real party name, no real partner work
  product, and no document containing real PII or real privileged
  content is uploaded to the PoC environment. Enforced at three layers:
  - Contractual (the addendum).
  - Procedural (checkbox on upload screen "أؤكد أن هذا المستند لا
    يحتوي على بيانات عميل حقيقية", required for non-admin users in
    demo env).
  - Technical (demo env carries env flag ENV=demo and the upload
    pipeline blocks documents flagged with pii_flags != [] from leaving
    the country — see below).

DATA FLOW UNDER THE EXCEPTION:
- Documents and embeddings: stored in KSA (Postgres, MinIO/S3, pgvector)
  — never leave the country.
- OCR: PaddleOCR self-hosted in KSA — never leaves.
- Embeddings inference: BGE-M3 self-hosted in KSA — never leaves.
- Arabic NER: CAMeL-Tools self-hosted in KSA — never leaves.
- Only the following leave KSA, and only to OpenAI:
  - Retrieved chunk text (top-k passages, max 5 × ~600 tokens = ~3000
    tokens) for Q&A.
  - First two chunks for auto-tagging classification.
  - First three chunks for summarization.
- Original PDFs, full document text, user identities, audit logs,
  search queries that aren't being answered by RAG — none of these are
  sent to OpenAI.

TECHNICAL ENFORCEMENT CONTROLS:

1. LLMClient is the ONLY code path that calls api.openai.com. All other
   outbound traffic from the VPC is blocked at the NAT egress allowlist
   except for connector targets (BOE, SAMA, National Platform domains).

2. Before any call to GPT-5, the LLMClient runs a pre-flight check:

   ```python
   def can_send_to_external_llm(doc: Document) -> bool:
       if doc.source_track == "track2_legacy":
           return False  # Track 2 not in PoC anyway; defense in depth
       if doc.privilege_flag:
           return False  # never send privileged content out
       if doc.pii_flags:  # national_id, iqama, iban, etc.
           return False  # never send PII out
       if doc.visibility == "restricted_matter":
           return False
       return True
   ```

   If the check fails, the system either refuses the Q&A operation with
   a clear Arabic message ("هذا المستند لا يدخل ضمن نطاق العرض
   التجريبي للمعالجة الخارجية") or falls back to a local-only path (in
   PoC, this means "no answer", since no local LLM is deployed).

3. The OpenAI API call is configured with headers OpenAI-Beta:
   no-training and uses zero data retention request when ETHKA's
   OpenAI account is eligible. ETHKA requests ZDR designation from
   OpenAI before week 4. If ZDR is not granted in time, demo proceeds
   under the exception but the addendum reflects standard retention.

4. Every call to GPT-5 writes an audit log entry to
   external_llm_calls table:
   ```json
   {
     "action": "external_llm_call",
     "model": "gpt-5",
     "purpose": "qa | autotag | summarize",
     "doc_id": "...",
     "doc_source_track": "track1_external | synthetic",
     "input_tokens": 2840,
     "output_tokens": 312,
     "latency_ms": 4210,
     "ts": "..."
   }
   ```
   This audit log is itself stored only in KSA.

5. The exception expires at the end of Phase 1. At pilot kickoff, the
   LLM swaps to a KSA-resident model and the production residency
   posture takes effect. The LLMClient swap is a one-line config
   change; call sites are unaffected.

PDPL ANALYSIS UNDER THIS SCOPE: because no personal data (Saudi
national ID, Iqama, real party names, real employee data, real client
matter data) is processed under the PoC, the PDPL "sensitive personal
data" trigger is not engaged. The exception is a COMMERCIAL decision
about IP exposure of synthetic firm content, not a PDPL waiver. ETHKA's
legal team confirms this analysis in writing before Al-Suhaiman signs
the addendum.

WHAT CODEX MUST IMPLEMENT TO ENFORCE 10.7:

15.2 FALLBACKS

- If a Track 1 connector hasn't fetched anything in the last 24h ->

  account settings ($50/day for demo env). Hitting cap fails Q&A calls
  open with canned refusal until rolled over.
- If upload pipeline takes >45 seconds live -> engineer pre-uploads
  during minute 0–1 narration and continues as if it just finished.
